# 自定义关卡导入设计

## 背景

当前项目已经包含桌面辅助工具 `tools/sokoban_level_generator.py`，可以设计推箱子关卡并导出 Dart 片段或 JSON 文件。Flutter App 目前只从 `lib/src/levels/sokoban_levels.dart` 读取内置关卡，用户导出的 JSON 还不能在运行时导入和游玩。

本文档用于定义后续扩展方向：让用户通过生成器导出关卡，再在 App 中导入，保存为自定义可玩关卡。

## 目标

- 支持导入生成器导出的 JSON 关卡。
- 导入后关卡出现在关卡选择页，并可正常进入游玩。
- 导入前进行严格校验，避免无效、显示异常或明显无解的关卡进入列表。
- 自定义关卡应独立于内置关卡保存，不需要重新编译 App。
- 设计保持可扩展，后续可以支持批量导入、删除、重命名、导出和 App 内编辑器。

## 非目标

- 第一版不在 App 内运行 `tools/sokoban_level_generator.py`。
- 第一版不支持在移动端直接启动 Python/Tkinter 生成器。
- 第一版不支持大于当前棋盘显示能力的超大关卡。
- 第一版不要求支持复杂关卡包、云同步或用户账号。

## 推荐用户流程

1. 用户在开发机或桌面环境运行：

   ```powershell
   python tools\sokoban_level_generator.py
   ```

2. 在生成器中设计关卡。
3. 点击“导出 JSON”，得到一个关卡 JSON 文件。
4. 打开 App 的关卡选择页。
5. 点击右上角“导入关卡”按钮。
6. 选择 JSON 文件或粘贴 JSON 文本。
7. App 解析并校验关卡。
8. 校验通过后保存为“自定义关卡”。
9. 自定义关卡显示在关卡选择页，可点击进入游玩。

## 入口设计

建议把导入入口放在关卡选择页，而不是隐藏在深层设置页。

原因：

- 用户导入后的直接目标是游玩新关卡，入口靠近关卡列表更自然。
- 导入结果可以立即反馈在同一页面。
- 后续删除、重命名、导出自定义关卡，也适合归属于关卡列表管理。

建议界面结构：

- AppBar 标题：`选择关卡`
- AppBar 右侧按钮：`导入`
- 页面分组：
  - `内置关卡`
  - `自定义关卡`
- 自定义关卡为空时显示简短空状态，例如 `还没有自定义关卡`

## JSON 数据格式

第一版直接兼容生成器当前导出的 JSON。

```json
{
  "number": 41,
  "title": "自定义关卡",
  "description": "把箱子推到目标点。",
  "layout": [
    "_______________",
    "_____###_______",
    "_____#T#_______",
    "____##B####____",
    "____#TB BT#____",
    "____###B###____",
    "______#T#______",
    "______###______",
    "_______________",
    "_______________"
  ],
  "initialPlayerPosition": {
    "row": 5,
    "column": 7
  }
}
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `number` | int | 关卡编号，仅作为展示来源，不作为唯一 ID |
| `title` | string | 关卡标题 |
| `description` | string | 关卡说明或提示 |
| `layout` | string[] | 棋盘布局 |
| `initialPlayerPosition.row` | int | 玩家初始行 |
| `initialPlayerPosition.column` | int | 玩家初始列 |

布局符号：

| 符号 | 含义 |
| --- | --- |
| `_` | 棋盘外或空白区域 |
| 空格 | 可行走地板 |
| `#` | 墙 |
| `B` | 箱子 |
| `T` | 目标点 |
| `*` | 已在目标点上的箱子 |

## 校验规则

导入时必须先校验，再保存。

硬性拒绝规则：

- JSON 无法解析。
- 缺少必需字段。
- `layout` 为空。
- `layout` 中存在非字符串行。
- 每一行长度不一致。
- 行数超过当前支持上限。
- 列数超过当前支持上限。
- 布局中存在非法字符。
- 玩家初始坐标越界。
- 玩家初始坐标位于 `_` 或 `#`。
- 玩家初始坐标与箱子重叠。
- 箱子数量为 0。
- 目标点数量为 0。
- 箱子数量与目标点数量不一致。
- 开局已有箱子在明确死格上。

当前 App 端尺寸上限：

- 最小视口：`10 x 10`
- 最大视口：`20 x 20`

`SokobanBoard` 会按关卡尺寸在 `10 x 10` 到 `20 x 20` 之间自动调整视口，并由页面按行列比例等比缩放到当前可用区域，保证已支持尺寸完整显示。

可选校验：

- 使用现有 `isSokobanStateSolvable` 检查是否可解。
- 如果可解性搜索耗时过长，应中断并提示用户关卡过复杂。
- 可以限制箱子数量，例如第一版最多 `6` 到 `8` 个箱子，避免搜索时间不可控。

## 编号与唯一 ID

不要把 JSON 中的 `number` 当作唯一标识。

原因：

- 用户导入的关卡编号可能和内置关卡重复。
- 多个自定义关卡之间也可能重复。
- 后续重命名或重新导入同一关卡时，需要稳定 ID。

建议保存时生成内部 ID：

```json
{
  "id": "custom_20260512_153012_001",
  "schemaVersion": 1,
  "importedAt": "2026-05-12T15:30:12+08:00",
  "level": {
    "number": 41,
    "title": "自定义关卡",
    "description": "把箱子推到目标点。",
    "layout": [],
    "initialPlayerPosition": {
      "row": 5,
      "column": 7
    }
  }
}
```

展示规则：

- 内置关卡继续显示 `1`、`2`、`3`。
- 自定义关卡可以显示 `自定义 1`、`自定义 2`。
- 详情或提示中可以保留原始 `number`，例如 `来源编号 41`。

## 存储设计

第一版推荐使用本地持久化保存自定义关卡列表。

可选方案：

| 方案 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| `shared_preferences` | 简单，适合少量 JSON | 不适合大量文件或复杂管理 | MVP 可用 |
| `path_provider` + JSON 文件 | 更适合关卡库、批量导入、备份 | 需要更多文件管理代码 | 长期推荐 |
| 内置 assets | 稳定，适合预置关卡包 | 需要重新构建 App | 不适合用户导入 |

建议长期结构：

```text
app_data/
  custom_levels/
    manifest.json
    custom_20260512_153012_001.json
    custom_20260512_153245_002.json
```

`manifest.json` 保存排序、标题索引和更新时间。单个关卡文件保存完整 JSON，方便未来导出、删除和修复。

## 代码结构建议

当前 `LevelSelectionPage` 和 `SokobanWallPage` 都直接依赖全局 `sokobanLevels`。支持运行时导入后，建议引入关卡目录层，避免页面直接绑定内置列表。

建议新增概念：

```dart
enum LevelSource {
  builtIn,
  custom,
}

class LevelCatalogItem {
  const LevelCatalogItem({
    required this.id,
    required this.source,
    required this.level,
  });

  final String id;
  final LevelSource source;
  final SokobanLevel level;
}
```

建议新增职责：

| 模块 | 职责 |
| --- | --- |
| `LevelParser` | 从 JSON 转成 `SokobanLevel` |
| `LevelValidator` | 校验结构、尺寸、数量、可解性 |
| `CustomLevelStore` | 读写本地自定义关卡 |
| `LevelCatalog` | 合并内置关卡和自定义关卡 |
| `LevelSelectionPage` | 展示目录和触发导入 |
| `SokobanWallPage` | 接收目录列表和初始索引进行游玩 |

`SokobanWallPage` 后续不应直接读取 `sokobanLevels`，而应接收当前可玩关卡列表。这样“下一关”“重置”“切换关卡”都能自然支持自定义关卡。

## 导入流程

建议流程：

1. 用户触发导入。
2. 获取 JSON 内容。
3. `LevelParser` 解析为临时数据对象。
4. `LevelValidator` 执行基础校验。
5. 执行死格检测。
6. 可选执行可解性检测。
7. 生成内部 ID。
8. 写入 `CustomLevelStore`。
9. 刷新 `LevelCatalog`。
10. 关卡选择页显示新关卡。

失败提示应明确可修复原因，例如：

- `第 4 行长度与第 1 行不一致`
- `箱子数量 3 与目标点数量 2 不一致`
- `玩家初始位置在墙上`
- `当前关卡尺寸为 21 x 20，当前最多支持 20 x 20`

## 平台注意事项

桌面端：

- 可以使用文件选择器导入 JSON。
- 生成器也更适合在桌面端运行。

Android：

- 不能假设用户能运行 Python 生成器。
- 文件导入需要处理系统文件选择、权限和 URI。
- 可以提供“粘贴 JSON 导入”作为更轻量的备用入口。

Web：

- 文件选择可行，但本地文件路径不可持久依赖。
- 存储适合使用浏览器本地存储。

## 安全与稳定性

- App 不应执行导入文件中的任何代码。
- 只解析 JSON 数据。
- 不读取 JSON 引用的外部路径。
- 限制文件大小，例如第一版最大 `64 KB`。
- 限制关卡尺寸和箱子数量，避免导入造成卡顿。
- 可解性检测应有超时或状态上限。

## 测试计划

单元测试：

- 有效 JSON 能解析为 `SokobanLevel`。
- 缺字段会失败。
- 非矩形布局会失败。
- 非法字符会失败。
- 箱子与目标点数量不一致会失败。
- 玩家越界会失败。
- 玩家在墙上会失败。
- `*` 同时计入箱子和目标点。

规则测试：

- 导入关卡可以复用 `positionsForSymbol`。
- 导入关卡可以复用 `computeDeadTiles`。
- 可选测试 `isSokobanStateSolvable` 对导入关卡生效。

Widget 测试：

- 关卡选择页能展示自定义关卡分组。
- 导入成功后出现新关卡。
- 点击自定义关卡能进入游戏页面。
- 删除或导入失败时不会影响内置关卡。

手动测试：

- 从 `tools/sokoban_level_generator.py` 导出 JSON 后导入。
- 导入重复编号关卡。
- 导入超尺寸关卡。
- 导入无解关卡。
- 重启 App 后自定义关卡仍存在。

## 分阶段实施

### 阶段 1：解析与校验

- 新增 JSON parser。
- 新增 validator。
- 给 parser 和 validator 添加单元测试。
- 暂不改 UI。

### 阶段 2：运行时目录模型

- 新增 `LevelCatalogItem`。
- 调整关卡选择页使用目录项。
- 调整游戏页接收关卡列表，而不是直接读取全局 `sokobanLevels`。
- 保持内置关卡行为不变。

### 阶段 3：导入入口与本地保存

- 在关卡选择页增加导入按钮。
- 支持选择 JSON 文件或粘贴 JSON。
- 导入成功后保存到本地。
- 重启 App 后加载自定义关卡。

### 阶段 4：自定义关卡管理

- 支持删除自定义关卡。
- 支持重命名标题和描述。
- 支持重新导出 JSON。
- 支持导入失败详情展示。

### 阶段 5：棋盘能力扩展

- 已将 `SokobanBoard.fixedRowCount` 和 `fixedColumnCount` 改为自适应视口。
- 已支持 `10 x 10` 到 `20 x 20` 的关卡缩放显示。
- 必要时支持滚动或拖拽查看棋盘。
- 重新评估生成器最大 `40 x 40` 是否适合 App 端游玩。

## 需要确认的问题

- 第一版是否只面向桌面端，还是 Android 也要同时支持？
- 第一版导入入口采用文件选择、粘贴 JSON，还是两者都支持？
- 自定义关卡是否需要和内置关卡混排，还是单独分组？
- 是否必须导入时验证“可解”，还是只做基础合法性校验？
- 是否允许导入超过 `20 x 20` 的关卡，并通过滚动或拖拽查看？

## 建议第一版验收标准

- 可以导入生成器导出的标准 JSON。
- 无效 JSON 不会保存，并给出明确错误。
- 导入后的自定义关卡能在关卡选择页看到。
- 点击自定义关卡能正常游玩、重置、撤销。
- 重启 App 后自定义关卡仍然存在。
- 内置 40 个关卡行为不变。
